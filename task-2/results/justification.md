# Task 2. Дизайн модуля пакетной обработки данных

Каждое утро в 06:00 интернет-магазину нужны кастомные CSV/XLS-прайс-листы для B2B-клиентов. Данные уже лежат в PostgreSQL (`products`, `categories`, `clients`, `client_prices`). Объём — 5–10 тысяч строк после join. Дополнительной бизнес-логики нет: связать таблицы и выгрузить файл. Инфраструктура — микросервисы в Kubernetes.

## Сравнительная таблица

Оценка: **низкая / средняя / высокая**. «Лучше» для этой задачи — то, что дешевле во внедрение и в ресурсы при простой выгрузке по cron.

| Критерий | Spring Batch | Apache Airflow | K8s CronJob | Spark |
|---|---|---|---|---|
| Наличие конфигурации CRON-расписания | Средняя: нужен отдельный планировщик (Quartz, Spring Scheduler) или внешний CronJob, который только стартует job | Высокая: timetable/DAG schedule из коробки | **Высокая: нативный `CronJob`, `schedule: "0 6 * * *"`** | Низкая: сам Spark не планирует, нужен Airflow/CronJob/Livy |
| Сложность реализации логики по обработке данных | Высокая мощность (chunk, skip, restart) — избыточна для SQL JOIN → CSV | Высокая мощность DAG — избыточна, когда шагов по сути один | **Низкая: SQL + запись файла в контейнере** | Высокая: кластер, job, сериализация — для 10k строк не нужна |
| Ресурсоёмкость | Средняя: JVM-приложение постоянно или на каждый запуск | Высокая: webserver + scheduler + metadata DB даже для одного DAG | **Низкая: под живёт минуты, затем исчезает** | Очень высокая: драйвер + executors |
| Масштабируемость под нагрузкой и сложность реализации | Высокая масштабируемость, средняя сложность — здесь нагрузка крошечная | Высокая масштабируемость, высокая сложность платформы | **Достаточная: 10k строк в одном поде; Horizontal scaling не требуется** | Избыточная масштабируемость, высокая сложность |
| Сложность развёртывания в облаке и интеграция с микросервисами | Средняя: ещё один Spring-сервис, CI/CD, реплики | Высокая: отдельная платформа оркестрации рядом с уже существующим k8s | **Низкая: тот же кластер, тот же registry, тот же манифест, что у сервисов** | Высокая: отдельный Spark-оператор / EMR / Dataproc |
| Удобство интеграции с логированием и мониторингом | Средняя: Actuator/Micrometer, но это ещё один тип приложения | Высокая: UI Airflow + метрики — ценой ещё одной системы | **Высокая: stdout → тот же стек, что у микросервисов (Prometheus, ELK)** | Средняя: Spark UI отдельно от общего стека |

## Вывод

Выбран **Kubernetes CronJob**.

Процесс — расписание плюс выгрузка, без ветвления, без миллиона строк, без Kafka/Spark. Airflow и Spark решают другую задачу (Task 1). Spring Batch оправдан, когда есть chunk-oriented ETL, restart и skip (Task 4). Здесь они добавили бы JVM-сервис ради `SELECT … JOIN` и записи CSV.

CronJob совпадает с уже принятым способом деплоя магазина: тот же кластер, образ из registry, логи в stdout, секреты БД как у остальных сервисов. Расписание — поле `schedule`, без второго оркестратора.

## Как будет работать решение (To Be)

Каждый день в 06:00 контроллер Kubernetes создаёт Job. Под стартует контейнер выгрузки, читает PostgreSQL (товары, категории, B2B-клиенты, клиентские цены), собирает кастомный прайс-лист на клиента и пишет CSV/XLS в объектное хранилище. B2B-клиенты забирают файлы из бакета. Под завершается, ресурсы освобождаются. При падении Job Kubernetes перезапускает его по `backoffLimit`; алерт берётся из тех же логов/метрик, что у микросервисов.
