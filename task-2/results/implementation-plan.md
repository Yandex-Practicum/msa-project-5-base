# Task 2. План конфигурации и имплементации

Верхнеуровневые шаги. Код выгрузки здесь не требуется — это дизайн.

1. **Уточнить контракт файла.** Для каждого B2B-клиента: колонки прайс-листа (SKU, категория, цена, валюта), CSV vs XLS, имя объекта в бакете (`prices/{client_id}/{yyyy-mm-dd}.csv`).
2. **SQL выгрузки.** Один запрос (или по клиенту в цикле): `products ⋈ categories ⋈ client_prices ⋈ clients`. Индексы по FK. На 10k строк хватает одного пода без партиционирования.
3. **Образ.** Минимальный контейнер (Python или Java) с клиентом Postgres и SDK объектного хранилища. Секреты БД и бакета — `Secret`, не в образе. Health/готовность не нужны: Job конечный.
4. **Манифест CronJob.** `schedule: "0 6 * * *"`, `concurrencyPolicy: Forbid` (не запускать второй под, если вчерашний ещё жив), `backoffLimit: 2`, `successfulJobsHistoryLimit: 3`, `failedJobsHistoryLimit: 3`, `ttlSecondsAfterFinished`. Ресурсы: CPU/RAM под один SQL и запись файла.
5. **Приёмник файлов.** Бакет (GCS/S3) + IAM для сервис-аккаунта пода. Локально в Minikube — PVC, в облаке — бакет. Политика жизни объектов (хранить N дней).
6. **Наблюдаемость.** Логи в stdout (сколько строк, какой клиент, путь объекта). Метрика «job failed» уже есть у kube-state-metrics. Алерт: CronJob не создал успешный Job после 06:15.
7. **Выкат.** Тот же GitOps/CI, что у микросервисов: сборка образа, манифест в overlay кластера магазина, секрет БД из того же хранилища секретов.
8. **Проверка.** Разовый `kubectl create job --from=cronjob/price-list-export manual-$(date)` на копии БД, сверка числа строк с `COUNT(*)` join'а, выборочный файл глазами.
9. **Эксплуатация.** Расписание 06:00 в TZ магазина (`spec.timeZone` в современном Kubernetes). Если выгрузка начнёт требовать ветвления или 10+ источников — это уже другой контекст (как Task 1), CronJob не растягивать в оркестратор.
