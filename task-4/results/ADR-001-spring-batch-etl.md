# Spring Batch как ETL складского отчёта

TradeWare принимает сменный складской отчёт целиком и обрабатывает его пакетом: валидация, обогащение справочником товаров, запись складских остатков. Команда — Java 11 / WildFly, цель — вынести обработку из HTTP-потока монолита в сервис рядом. Выбран **Spring Batch** (Spring Boot-приложение): один принятый отчёт = один job instance, chunk-oriented запись, skip/retry/restart, метрики Micrometer. Airflow отвергнут — это оркестратор графа из многих источников, а не Java-ETL файла; Spark/Dataflow — избыточны на 2k–400k строк; голый Kubernetes Job со скриптом не даёт chunk/restart и хуже стыкуется с Java-монолитом.

## Status

accepted

## Considered Options

- **Spring Batch (выбран).** Тот же язык, что монолит; job repository; 100–150 параллельных job instance на пике; постепенный вынос из WildFly.
- **Apache Airflow.** Нужен в маркетинговом пайплайне (Task 1), здесь граф из Kafka/Spark не требуется. Другая платформа, другой стек, другой on-call.
- **Spark / Cloud Dataflow.** Имеет смысл на десятках миллионов строк и тяжёлых трансформациях. На отчёте в 2 000–400 000 строк цена кластера не окупается.
- **K8s Job со скриптом.** Достаточно для «SELECT → CSV» (Task 2/3). Здесь нужны рестарт с чекпоинта, skip битых строк, метрики прогона — это Batch, не bash.

## Consequences

- HTTP-приёмка в WildFly остаётся тонкой: валидация формата, запись в GCS, «принято».
- Появляется отдельный сервис и job repository (Postgres). Это плата за разгрузку ERP.
- Лид уже знает Spring Batch — срок внедрения короче, чем у смены стека.
