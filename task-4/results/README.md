# Task 4. ETL складского отчёта на Spring Batch

## Проблемы кейса

Монолит WildFly обрабатывает CSV **построчно в HTTP-запросе**. Сотрудник склада ждёт окончания прогона во вкладке. На пике (до 400k строк/сутки, в 2–3 раза больше в сезон, 100–150 параллельных загрузок) ERP «висит», обновления остатков опаздывают, API партнёров блокируются. Логов в файл и мониторинга VM недостаточно, чтобы собрать картину сбоя.

Корень — не UI и не справочник товаров, а отсутствие пакетной обработки: приёмка файла смешана с ETL.

## Решение

См. [ADR-001-spring-batch-etl.md](ADR-001-spring-batch-etl.md) и [ADR-002-last-accepted-report-wins.md](ADR-002-last-accepted-report-wins.md).

Кратко:

1. Складской отчёт — документ смены. WildFly принимает файл, кладёт в GCS, отвечает «принято». Ошибка формата — сразу в HTTP.
2. Отдельный сервис Spring Boot + Spring Batch: один принятый отчёт = один прогон (валидация → обогащение справочником → запись остатков).
3. 30 секунд на 2 000 строк — длительность **прогона**, не HTTP.
4. 100–150 параллельных **приёмок**; число воркеров Batch ограничено отдельно; очередь принятых отчётов — штатная метрика.
5. Результат прогона — WebSocket в Angular. Алерт дежурным — не сотруднику склада.

Альтернативы (Airflow, Spark/Dataflow, K8s Job) разобраны в ADR-001. Мониторинг и логи — Task 5.
