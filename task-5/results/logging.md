# Обоснование способа отправки логов

Сейчас логи пишутся в файл на VM WildFly. На пике нельзя склеить приёмку, запись в GCS, прогон Batch и WebSocket в одну историю. Нужен централизованный поиск по **одному** идентификатору складского отчёта.

## Выбор: ELK + Filebeat + JSON в stdout

| Способ | Почему да / нет |
|---|---|
| **JSON в stdout + Filebeat → Elasticsearch → Kibana** | Приложения не знают про кластер логов. Тот же паттерн, что у будущих микросервисов. Filebeat легче Logstash-агента на каждой VM. `reportId` в каждой строке склеивает картину |
| Logstash как единственный агент на VM | Умеет парсить неструктурированные логи WildFly, но тяжелее. Имеет смысл как *опциональный* пайплайн, если нельзя сразу перейти на JSON |
| Копировать файлы раз в час | Статус-кво: задержка и нет корреляции |
| HTTP POST из приложения в Elasticsearch | Приложения начинают зависеть от ELK; при падении ES страдает приёмка отчётов |
| Только Cloud Logging | Честный путь на GCP, но задание явно включает ELK; в тексте фиксируем, что в облаке Filebeat можно заменить агентом Google |

## Контракт лога

Каждая запись JSON:

- `timestamp`, `severity`, `service` (`wildfly` / `stock-report-batch`)
- `reportId` — обязателен с момента приёмки
- `event`: `format_rejected` | `accepted` | `job_started` | `job_failed` | `job_completed`
- `warehouseId` там, где известен

Без `reportId` Kibana снова превращается в четыре несвязанных файла.

## Поток

1. WildFly и Spring Batch пишут JSON в stdout (или в файл, который Filebeat хвостает).
2. Filebeat на VM/поде шлёт в Elasticsearch.
3. Kibana: сохранённый поиск по `reportId`.
4. Grafana берёт метрики из Prometheus; переход в логи — по тому же `reportId`.

Алерты Alertmanager не дублируют WebSocket сотруднику. Логи ошибки формата нужны поддержке («какой файл отклонили»), но не будят дежурного.
